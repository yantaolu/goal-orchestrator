# 目标规划与情景推演协议

本协议用于所有 `goal_realization` 请求。它把一句目标主动构造成可规划意图和能够指导选择与行动的规划，并让情景推演检查路径能否在现实变化中工作。短输入不等于简单目标。它不要求完整虚拟团队，也不规定固定报告标题。

## 先形成目标简报

从用户原话主动构造暂定 Goal Brief，不要求用户先填写表格：

- **现实变化：** 谁或什么将从当前状态变成什么状态。
- **对象与受益者：** 谁使用、负责、受影响或从中获益。
- **成功信号：** 哪些可观察结果表示方向有效，哪些表示目标已达成。
- **边界：** 已知期限、资源、范围、明确排除项和不能突破的约束。
- **关键未知：** 哪些未知会改变范围、路径或风险判断。
- **推进假设：** 用哪些最小、可逆的假设先形成版本；必要时保留哪个条件分支。

在用户可见答案中，用一两句自然语言给出“我先按什么目标理解”，随后直接进入建议。不机械展示六字段，也不问“你想要哪种方案”。

### 什么时候前置提问

默认先交付再校准。只有以下情况才先问一个问题：

- 不同答案会导致目标对象或路线完全不同。
- 选择会造成重大且难以撤回的资金、法律、安全、健康或数据风险。
- 缺少回答后无法给出任何负责任的默认路径或安全分支。

若能用“在 A 条件下先走路径一；若 B 成立则切换路径二”继续，就先规划。一般偏好、具体数字和可迭代范围放在结尾询问。

## 选择规划与推演深度

`planning_depth` 看的是目标复杂度：

| 深度 | 典型条件 | 需要形成的价值 |
|---|---|---|
| `light` | 单一、短期、低风险、易调整 | 自然步骤、节奏、检查点、安全边界和第一步 |
| `standard` | 有多个结果、依赖或阶段，需要持续数周至数月 | 目标状态、关键机制、结果拆解、依赖、阶段成果、判断门、失败路线和调整信号 |
| `deep` | 规模大、多方参与、多层组织、强耦合、高风险、长周期、难逆转或持续运营 | 完整运营模型、权责与信息机制、候选路径、阶段转换、代表性场景推演和可操作修订 |

`goal_realization` 默认至少 `standard`；明显简单的个人目标可以降为 `light`。不要因为输入只有一句话而降级。

`simulation_depth` 看的是场景能否揭示路径缺口：

- `none`：场景不会改变方案，或问题只是简单说明。
- `light`：一个高辨识度的正常、压力或失败场景。
- `structured`：少量互补场景，至少覆盖正常运行和压力／失败中的相关部分。

## 构造目标状态和运营模型

先回答“目标实现后，系统怎样持续工作”，再决定项目阶段。按领域选择真正相关的机制：

- 产品目标：用户旅程、价值闭环、能力边界、数据与反馈。
- 经营目标：客群、价值主张、获客、转化、复购、单位经济性和经营节奏。
- 管理目标：组织单元、管理跨度、授权、目标传导、信息回流、干部机制和异常升级。
- 组织变革：未来运行方式、权责迁移、过渡态、利益相关者、采用与反弹机制。
- 个人目标：能力递进、练习节奏、恢复、安全和进步信号。

目标状态必须能解释因果关系，而不是写“建立机制、加强协同、持续优化”。例如管理大型事业部时，应说明业务单元怎样划分、哪些权力下放、经营数据怎样逐级汇总、例外怎样升级，以及负责人如何被评价和替换。

## 拆解结果与形成路径

从结果而不是岗位或活动开始：

1. 将目标拆成少量能够共同构成成功的关键结果。
2. 为每个结果确定前置依赖、可观察产出和判断标准。
3. 识别至少一条推荐路径；只有重大未知或取舍存在时才保留候选路径。
4. 形成有意义的阶段，每个阶段都产生能改变下一步决定的成果。
5. 写清继续、暂停、调整、回退或停止的信号。
6. 选择今天或本周能够启动且能降低最大不确定性的现实首步。

阶段不是日历切片。若一个阶段只有“推进、优化、加强”，却没有阶段成果和判断门，就没有规划价值。

## 向前推演代表性场景

情景推演沿目标机制向前运行，不是补一个风险清单。每个场景至少跟踪：

1. **触发：** 什么变化或事件发生。
2. **感知：** 哪个信号最先出现，谁能看到。
3. **决策：** 哪项规则、权力或阈值被调用。
4. **行动与交接：** 谁做什么，信息或成果怎样流转。
5. **结果与恢复：** 正常路径、失败路径和恢复条件。
6. **暴露缺口：** 哪个职责、接口、数据、权限或门槛不成立。

选择最少但有辨识度的场景：

- **正常场景：** 检查日常机制能否低摩擦运行。
- **压力场景：** 需求、规模、时间、资源或冲突突然增大。
- **失败场景：** 关键结果未达成、关键人退出、系统失效或重大例外发生。

例如大型事业部可选择战略突然变化、一个业务单元连续不达标、重大客诉横跨多部门、核心干部离职等。不要为了完整机械推演全部；选择最可能改变组织设计的一到三个。

## 将发现变成方案修订

推演只有进入规划才创造价值。每个重要发现都要产生具体修订，使用简短闭环记录：

```text
场景触发 → 暴露缺口 → 修改哪项机制 → 修改后的判断或恢复方式
```

可接受的修订包括：

- 改变决策权、升级条件或责任边界。
- 增加阶段门、回退路线、缓冲或替代路径。
- 改变数据、指标、信息传递频率或异常可见性。
- 调整模块接口、组织跨度、资源优先级或验证顺序。
- 缩小首期范围，先验证决定性假设。

仅写“加强沟通、关注风险、建立预案”不算修订。输出至少展示一个“因为推演发现 X，所以方案从 A 改为 B”的具体变化；`structured` 应覆盖最关键的多个变化，但只展示影响结论的部分。

## 形成现实实施指南

按相关性整合，而不是照抄固定章节：

- 暂定可规划目标及重要假设。
- 推荐的目标状态、产品／业务／管理方案或运营模型。
- 关键结果、依赖和优先顺序。
- 阶段成果，以及进入下一阶段的判断门。
- 代表性场景暴露的缺口和已做的修订。
- 主要失败路线、回退或停止条件。
- 观察和调整信号。
- 能立即启动的现实第一步。

责任映射只在责任会影响实施时加入；完整模拟团队只在跨专业生产与独立审查确有价值时加入。真实组织本身可以是规划主体，不因此触发虚拟团队。

## 信息价值检查

回答前检查：

- 用户是否无需再次解释“到底想要什么”就能看到一个合理的暂定目标？
- 目标状态是否描述了怎样运作，而不仅是愿景？
- 关键结果之间是否有因果、依赖或优先关系？
- 每个重要阶段是否产生可验收成果并影响下一步？
- 是否有继续、调整、失败或停止的判断信号？
- 场景是否真的沿机制运行，并至少修改了一项方案？
- 是否给出一个现实可启动的第一步？
- 是否避免用固定标题、全生命周期、虚拟角色或篇幅代替领域内容？

若缺失的是内容，补机制和判断；若缺失的只是形式，不必补栏目。
